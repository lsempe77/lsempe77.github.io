Finite prefixes, cached states, and the limits of long-context generation

Chapter orientation

Why this chapter matters

A decoder language model predicts the next token from a finite permitted prefix. The maximum number of tokens it can process is the context window. This limit affects what evidence is available to a prediction, the memory required by attention, the latency of generation, and the interpretation of claims that a model has “read” a long document.

Inference is also sequential. A generated token becomes part of the next prefix. Key-value caching avoids recomputing the representations of earlier tokens at every step, but it retains an expanding memory state. This chapter defines these mechanics and the evidence needed to assess long-context use. Chapter 28 treats how tokens are selected from the next-token distribution.

Learning objectives

By the end of this chapter, you should be able to:

  • distinguish context length, generated length, and total sequence length;
  • explain why causal decoding is sequential even when prompt processing is parallel;
  • calculate the shape and approximate storage of a key-value cache;
  • compare full-prefix recomputation with cached decoding;
  • identify the difference between fitting text into a context and using relevant information from it;
  • state common long-context evaluation failures; and
  • specify an inference record that makes latency and length claims interpretable.

Running sequence

We use a prompt of five token IDs and generate three new IDs. A maximum context of six means that a later prediction cannot retain every original prompt token if the system uses a sliding window.

Level 1 - Intuition

A context window is an information boundary

The context window is a token limit, not a guarantee that every retained token affects an answer. A token outside the window cannot be attended to by an ordinary finite-context decoder. A token inside it is available in principle, but the model may assign it little attention, fail to retrieve it among distractors, or use it incorrectly. “Supports 32,000 tokens” therefore describes an input capacity, not a measured ability to answer questions about every position in a 32,000-token document.

The boundary is measured after tokenisation. A page, a word count, or a character count has no fixed conversion because language, formatting, code, and tokeniser affect the number of IDs. Prompts also consume the same budget as generated output in most interfaces. A requested answer can fail because the prompt plus reserved output exceeds the configured total length.

Prompt processing and generation are different phases

During prompt processing, a causal Transformer can compute representations for supplied positions in parallel under its causal mask. This is commonly called prefill. Once generation begins, token (t+1) cannot be selected until the model has processed the selected token (t). Output is therefore sequential even on highly parallel hardware.

The difference helps interpret latency. A long prompt can create a substantial initial wait before the first new token. A long generated answer can be slow because it requires repeated decode steps. Reporting only total tokens per second mixes these phases and obscures the user-facing bottleneck.

Code 
prompt=np.array([2,11,34,58,3]); generated=[]
for chosen in [17,29,3]:
    print("prefix length before selection:",len(prompt)+len(generated),"choose:",chosen)
    generated.append(chosen)

Level 2 - Cache mechanics

Why naive decoding repeats work

Without a cache, generating each new token recomputes attention projections for the full prefix. For a prefix length (L), the next step uses length (L+1), then (L+2), and so on. Earlier tokens are repeatedly projected even though their keys and values do not change in a causal decoder.

A key-value cache stores the key and value tensors produced at each layer for earlier positions. At the next step, the new query attends to stored keys and values plus the new token’s key and value. The cache does not make generation parallel, but it avoids repeatedly rebuilding the earlier prefix.

Cache shape and memory

For batch size (B), layers (n_l), key-value heads (n_{kv}), head width (d_h), and cached length (L), keys and values require approximately

[ 2B n_l n_{kv} L d_h ]

stored numbers. Multiply by bytes per number to obtain a rough memory estimate. Multi-query and grouped-query attention reduce (n_{kv}) relative to the number of query heads, lowering cache memory without changing the causal sequence rule.

Code 
B,layers,kv_heads,length,head_dim,bytes_per=1,32,8,8192,128,2
cache_bytes=2*B*layers*kv_heads*length*head_dim*bytes_per
print(f"KV cache: {cache_bytes/2**30:.2f} GiB")

The estimate excludes model weights, activations required by the serving system, allocator overhead, metadata, and temporary attention buffers. It is useful for identifying linear growth with context length, not for replacing a measured memory profile.

Cache correctness is a model test

Cached decoding should agree with full-prefix decoding for the same model, tokens, position treatment, masks, and numerical precision within an explicit tolerance. Disagreement can arise from wrong cache positions, stale entries, incorrect padding handling, rotary-position implementation, or an inconsistency between prefill and decode code paths.

Code 
full_prefix_logits=np.array([.1,.2,.7])
cached_logits=np.array([.1,.2,.7])
assert np.allclose(full_prefix_logits,cached_logits,atol=1e-6)
print("cached and full-prefix reference outputs agree")

Level 3 - Long-context use

Cost grows before the cache is available

The cache improves repeated decoding but does not remove the cost of processing a long initial prompt. Standard dense self-attention forms score relations among positions during prefill, so the attention component grows quadratically with sequence length. Chapter 20 derived this relation. Implementation methods can reduce memory traffic and avoid materialising the full score matrix, but they do not make every long prompt free.

Long-context systems may modify the architecture, position method, attention pattern, cache representation, or retrieval pipeline. These choices create different failure modes. A sparse attention pattern restricts which positions can interact directly. A position method may be trained or extrapolated over a limited range. Retrieval can select a subset of external documents, but it does not prove that omitted text was irrelevant. Each mechanism needs evaluation at the position, length, and document structure for which it will be used.

Retrieval is not identical to longer context

Retrieval can reduce the prompt to passages selected from a larger collection. It changes the inference problem from attending over all supplied text to selecting and using evidence. A large window may contain an entire document; it still must locate and apply the relevant information. Chapter 33 will examine retrieval-augmented generation as a complete system, including indexing and evaluation.

Code 
document_tokens=20_000; retrieved_tokens=1_500; window=4_096
print("full document fits window:",document_tokens<=window)
print("retrieved subset fits window:",retrieved_tokens<=window)

Context extension needs an explicit comparison

A model may be trained at one maximum length and served at another. Position representations, training examples, attention kernels, and optimisation all affect whether behaviour transfers beyond the length distribution seen during training. A larger configured limit therefore requires a comparison with a stated baseline: the same task at the original and extended lengths, evidence placed across positions, and a record of any change to position handling or continued training.

Long inputs can also conceal a simpler problem: the relevant evidence may be absent from the retained prefix. Sliding-window policies remove older tokens; fixed prompt templates may reserve too little output; and document conversion can add headings, markup, or duplicated material that consumes capacity. The input trace should retain token counts before and after formatting, the truncation decision, and the final token positions supplied to the model.

The policy should distinguish discarded context from an intentional summary or retrieved representation. A summary is new model-generated text that may omit or distort facts. Retrieval is selected external evidence. Cached tokens are exact retained activations for previous IDs. These mechanisms can be combined, but their information properties differ and they should not be described by one generic claim of “memory”.

Serving constraints change the available context per request

At deployment, many requests may share accelerator memory. Each active sequence has a cache length, and a serving scheduler chooses batching, admission, eviction, and output limits. A context limit that fits one request can reduce concurrency or exceed memory under a busy workload. Conversely, aggressively capping prompts can improve latency while discarding evidence needed for a task. These are operating choices that should be measured against the task and service requirement.

Code 
cache_per_request_gib=1.0
available_gib=24
for active in [1,8,16,24]:
    print(active,"active requests require",active*cache_per_request_gib,"GiB of cache")

The calculation is deliberately incomplete because weights, temporary buffers, and allocator behaviour also occupy memory. It makes one relationship visible: higher concurrency, longer retained prefixes, and larger cache representations compete for the same hardware capacity. A serving result should specify whether its reported throughput is for isolated or concurrent requests, along with the prompt-length distribution.

Long-context errors require traces, not only accuracy totals

When a model misses evidence in a long prompt, a useful diagnostic records the original document, tokenised length, retained window, evidence span, retrieval or packing decision, generated tokens, and scoring rule. This can separate an error caused by truncation from one caused by poor retrieval, position sensitivity, or an incorrect answer despite available evidence. Aggregate accuracy remains useful, but it cannot make these failure modes distinguishable.

Code 
trace={"document_tokens":9100,"retained_tokens":8192,"evidence_position":7800,"truncated":False,"answer_correct":False}
print(trace)

Position and distraction controls should vary one feature at a time. For example, hold the question and answer constant while moving evidence from early to middle and late positions; then add unrelated material while keeping the evidence position fixed. These comparisons reveal whether a score changes with length, location, or competing content. They provide stronger evidence than a single long document with a single successful answer.

Level 4 - Audit and reporting

Length claims need tests that control position and distraction

A useful long-context evaluation places known evidence at several positions, asks a defined question, and compares performance across lengths and numbers of distractors. It should distinguish exact retrieval of a stated item from multi-step use of several items. Repeating a short fact many times, testing only the beginning of a prompt, or scoring a single favourable example cannot establish broad long-context use.

The evaluation should also record tokeniser, actual valid lengths, truncation and packing policy, prompt template, generation limit, sampling rule, and whether the answer was checked automatically or by people. Changing any of these can change the test. An answer that fails may reflect missing evidence, truncation, retrieval failure, cache error, decoding variation, or the model’s conditional distribution; the trace should make those possibilities distinguishable.

Code 
positions=[128,1024,4096,7168]
results={p:None for p in positions}
print("record evidence position and outcome:",results)

An inference record separates capacity from service quality

An inference report should include model and tokenizer version, context limit, maximum output length, prompt and output token distributions, prefill latency, decode latency or tokens per second, cache precision and layout, batch policy, hardware, concurrency, truncation behaviour, and failure policy. At least one cache-equivalence test and one boundary test at the configured maximum length should be retained.

The record supports operational decisions. It can show whether a system is limited by long-prompt prefill, by per-token decode latency, by memory available for concurrent caches, or by a context policy that discards needed evidence. A model card that says only “long context” cannot answer those questions.

Code 
inference_record={"context_limit":8192,"prompt_tokens":6200,"max_new_tokens":512,"prefill_ms":740,"decode_tokens_per_second":55,"cache_dtype":"float16"}
assert inference_record["prompt_tokens"]+inference_record["max_new_tokens"]<=inference_record["context_limit"]
print("length-budget check passed")

Common misconceptions

  • A context limit is a guarantee of long-document reasoning. It specifies input capacity, not measured use of every position.
  • Caching makes generation parallel. It removes repeated prefix computation but each selected token still conditions the next step.
  • The cache stores the whole model state at no cost. It grows with layers, batch size, key-value heads, head width, and length.
  • A document fits in context, so no truncation policy is needed. Prompt templates and reserved output also consume the total budget.
  • Retrieval and a longer window solve the same problem. Retrieval selects evidence; a window determines available token capacity.

Summary

Context windows define a finite token-level information boundary. Long prompts create prefill cost, and sequential generation requires one conditional decision after another. Key-value caches avoid repeated projection of earlier tokens but grow linearly with retained sequence length and must be tested against full-prefix decoding.

Capacity, retrieval, and demonstrated long-context use are distinct claims. Chapter 28 compares the policies that select tokens from a next-token distribution; Chapter 33 examines retrieval-augmented generation as a complete pipeline.

Looking ahead

The context window and cache determine which prefix the model can condition on and the cost of extending it. Chapter 28 examines the further policy that turns each next-token distribution into an emitted sequence.

```{python}
    print(active,"active requests require",active*cache_per_request_gib,"GiB of cache")
```

The calculation is deliberately incomplete because weights, temporary buffers, and allocator behaviour also occupy memory. It makes one relationship visible: higher concurrency, longer retained prefixes, and larger cache representations compete for the same hardware capacity. A serving result should specify whether its reported throughput is for isolated or concurrent requests, along with the prompt-length distribution.

### Long-context errors require traces, not only accuracy totals

When a model misses evidence in a long prompt, a useful diagnostic records the original document, tokenised length, retained window, evidence span, retrieval or packing decision, generated tokens, and scoring rule. This can separate an error caused by truncation from one caused by poor retrieval, position sensitivity, or an incorrect answer despite available evidence. Aggregate accuracy remains useful, but it cannot make these failure modes distinguishable.

```{python}
trace={"document_tokens":9100,"retained_tokens":8192,"evidence_position":7800,"truncated":False,"answer_correct":False}
print(trace)
```

Position and distraction controls should vary one feature at a time. For example, hold the question and answer constant while moving evidence from early to middle and late positions; then add unrelated material while keeping the evidence position fixed. These comparisons reveal whether a score changes with length, location, or competing content. They provide stronger evidence than a single long document with a single successful answer.

## Level 4 - Audit and reporting

### Length claims need tests that control position and distraction

A useful long-context evaluation places known evidence at several positions, asks a defined question, and compares performance across lengths and numbers of distractors. It should distinguish exact retrieval of a stated item from multi-step use of several items. Repeating a short fact many times, testing only the beginning of a prompt, or scoring a single favourable example cannot establish broad long-context use.

The evaluation should also record tokeniser, actual valid lengths, truncation and packing policy, prompt template, generation limit, sampling rule, and whether the answer was checked automatically or by people. Changing any of these can change the test. An answer that fails may reflect missing evidence, truncation, retrieval failure, cache error, decoding variation, or the model's conditional distribution; the trace should make those possibilities distinguishable.

```{python}
positions=[128,1024,4096,7168]
results={p:None for p in positions}
print("record evidence position and outcome:",results)
```

### An inference record separates capacity from service quality

An inference report should include model and tokenizer version, context limit, maximum output length, prompt and output token distributions, prefill latency, decode latency or tokens per second, cache precision and layout, batch policy, hardware, concurrency, truncation behaviour, and failure policy. At least one cache-equivalence test and one boundary test at the configured maximum length should be retained.

The record supports operational decisions. It can show whether a system is limited by long-prompt prefill, by per-token decode latency, by memory available for concurrent caches, or by a context policy that discards needed evidence. A model card that says only “long context” cannot answer those questions.

```{python}
inference_record={"context_limit":8192,"prompt_tokens":6200,"max_new_tokens":512,"prefill_ms":740,"decode_tokens_per_second":55,"cache_dtype":"float16"}
assert inference_record["prompt_tokens"]+inference_record["max_new_tokens"]<=inference_record["context_limit"]
print("length-budget check passed")
```

## Common misconceptions

- **A context limit is a guarantee of long-document reasoning.** It specifies input capacity, not measured use of every position.
- **Caching makes generation parallel.** It removes repeated prefix computation but each selected token still conditions the next step.
- **The cache stores the whole model state at no cost.** It grows with layers, batch size, key-value heads, head width, and length.
- **A document fits in context, so no truncation policy is needed.** Prompt templates and reserved output also consume the total budget.
- **Retrieval and a longer window solve the same problem.** Retrieval selects evidence; a window determines available token capacity.

## Summary

Context windows define a finite token-level information boundary. Long prompts create prefill cost, and sequential generation requires one conditional decision after another. Key-value caches avoid repeated projection of earlier tokens but grow linearly with retained sequence length and must be tested against full-prefix decoding.

Capacity, retrieval, and demonstrated long-context use are distinct claims. [Chapter 28](28-decoding-generation.qmd) compares the policies that select tokens from a next-token distribution; Chapter 33 examines retrieval-augmented generation as a complete pipeline.
