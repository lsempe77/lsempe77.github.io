Changing a model for a task while controlling memory, storage, and regressions

Chapter orientation

Why this chapter matters

Fine-tuning adapts a pretrained checkpoint to a declared task or response distribution. Full fine-tuning updates all trainable model parameters. Parameter-efficient fine-tuning (PEFT) freezes most base weights and trains a smaller set of added or selected parameters. The choice affects optimiser memory, checkpoint storage, deployment, multi-task serving, and the kinds of changes a run can represent.

Neither method removes the need for data documentation or evaluation. A small adapter can overfit, encode an unsafe behaviour, or fail outside its tuning distribution. A full update can improve a target task while degrading retained behaviours. This chapter gives the comparison and the implementation contracts required to make it interpretable.

Learning objectives

By the end of this chapter, you should be able to:

  • distinguish full fine-tuning, frozen-base adaptation, and inference-only prompting;
  • derive the parameter count of a low-rank update;
  • explain LoRA’s update and merge operation;
  • compare weight, gradient, optimiser-state, and activation memory;
  • identify adapter/checkpoint compatibility requirements;
  • evaluate target gains and retained-task regressions; and
  • record an adaptation run so that it can be reproduced or served safely.

Running layer

For a linear layer with base weight (W), LoRA learns a low-rank update (W = BA). The base weight remains frozen during training, and the update can be applied separately or merged into a copy of the base weight for inference.

Level 1 - Intuition

Adaptation changes a checkpoint under a task distribution

Full fine-tuning applies gradients to all selected model weights. It can represent broad changes, but it requires storing gradients and optimiser state for those weights and usually produces a full new checkpoint. Parameter-efficient methods retain the base checkpoint and train a smaller module, such as low-rank matrices, adapters, prompts, or selected bias terms. This makes it possible to store task-specific changes separately and load different adaptations over one base model.

The methods are not ordered by quality in the abstract. The relevant comparison depends on task complexity, data size, available hardware, update frequency, latency constraints, compatibility requirements, and the cost of keeping several adapted versions. A smaller update reduces trainable parameters; it does not make the task specification or evaluation smaller.

Code 
base_parameters=7_000_000_000
adapter_parameters=8_000_000
print("trainable fraction:",adapter_parameters/base_parameters)

Frozen weights are still part of the function

A PEFT adapter is not a standalone model. It assumes a particular base checkpoint, architecture, tokenizer, layer naming convention, target modules, rank, scaling rule, and often quantisation configuration. Loading an adapter onto a related model with the same visible size can change or break its function. The serving record must bind the adapter to its compatible base.

Code 
adapter_metadata={"base":"checkpoint-v1","target_modules":["q_proj","v_proj"],"rank":8,"scale":16}
print(adapter_metadata)

Level 2 - LoRA mechanics

Low-rank updates reduce trainable parameter count

For a layer (W^{d_{out}d_{in}}), a full update contains (d_{out}d_{in}) parameters. A rank-(r) LoRA update uses (A^{rd_{in}}) and (B^{d_{out}r}), for (r(d_{in}+d_{out})) trainable parameters. The update is commonly scaled by a factor such as (/r) (Hu et al. 2022).

Code 
d_in,d_out,r=4096,4096,8
full=d_in*d_out; lora=r*(d_in+d_out)
print("full parameters:",full,"LoRA parameters:",lora,"fraction:",lora/full)

The reduction is largest when rank is much smaller than layer widths. Targeting only some projections reduces it further. These decisions restrict the trainable update family. They can be sufficient for a task, but sufficiency should be demonstrated on target and retained evaluations, not inferred from a low training loss.

Merge and unmerge are numerical operations

At inference, an adapter can be applied as a separate branch or merged by forming (W’ = W + sBA). Merging can reduce runtime overhead, but it creates a new effective weight tensor. Repeated merging, wrong scaling, mismatched dtype, or merging into the wrong base can produce irreversible errors unless the original base and adapter are retained.

Code 
np.random.seed(2)
W=np.random.randn(3,4); A=np.random.randn(2,4); B=np.random.randn(3,2); scale=.5
x=np.random.randn(4)
separate=W@x+scale*(B@(A@x))
merged=(W+scale*B@A)@x
assert np.allclose(separate,merged)
print("separate and merged adapter outputs agree")

Level 3 - Resource and deployment accounting

Trainable parameters are not the whole memory account

Training memory includes base weights, trainable weights, gradients, optimiser states, activations, temporary buffers, and communication state. Freezing a base model can remove its gradient and optimiser-state requirements, but the base weights and many forward activations remain. Quantising frozen weights can lower storage further, while introducing a new numerical configuration that must be evaluated. QLoRA combines quantised base weights with low-rank adapters (Dettmers et al. 2023).

Code 
params=7_000_000_000; bytes_per_weight=2; bytes_per_adam_state=8
full_weight_gib=params*bytes_per_weight/2**30
full_adam_gib=params*bytes_per_adam_state/2**30
print("base weights GiB:",round(full_weight_gib,1),"Adam moments GiB:",round(full_adam_gib,1))

Multi-adapter serving creates routing decisions

Separate adapters can make several task variants cheaper to store than several full checkpoints. Serving still needs a policy for selecting the adapter, ensuring it is compatible with the request, batching requests that use different adapters, and preventing an adapter intended for one task or policy from being silently applied to another. An adapter identifier is part of the request and audit trace.

Code 
routes={"legal-summary":"adapter-legal-v2","code-review":"adapter-code-v1"}
request_task="code-review"
print("selected adapter:",routes[request_task])

Parameter scope is a substantive design choice

PEFT is a family of methods rather than one fixed architecture. An implementation may target attention projections, feed-forward layers, output heads, selected biases, or inserted adapter blocks. Each scope changes which transformations can adapt and how many new parameters are trained. The scope should be reported at the level of module names and layer coverage, not only as a total trainable-parameter count.

Targeting all layers can permit a more distributed adaptation than targeting only a final projection. Targeting a small subset can reduce storage and training time while concentrating the burden of adaptation in fewer locations. The appropriate choice is empirical: test candidate scopes on the declared task and retained suite under the same data and optimisation budget.

Checkpoint organisation determines recoverability

An adaptation run should preserve the immutable base identifier, adapter weights, configuration, tokenizer and template versions, training state where resumption is required, and evaluation records. A merged weight file alone can make a task variant convenient to serve, but it loses the clean separation between base and update unless both original artefacts are retained. A safe workflow treats merging as a reproducible build step with an output hash and an equivalence test.

Code 
checkpoint={"base_hash":"abc","adapter_hash":"def","merge_scale":16/8,"merged":False,"template":"v3"}
assert checkpoint["base_hash"] and checkpoint["adapter_hash"]
print("recoverable adapter checkpoint metadata present")

Data volume and update scope interact

An adapter with few trainable parameters does not imply that many examples are required, nor does a full update imply that a small dataset is necessarily unsuitable. The relevant risk depends on how far the target distribution differs from the base model, how repetitive the data are, how many update tokens and epochs are used, and which evaluation tasks must remain stable. A small, tightly specified adaptation can overfit through either method when the validation split duplicates templates or sources.

Checkpoint selection should inspect learning curves and held-out behaviour across more than one update count. A model that reaches its best target score early may degrade after additional passes over narrow data. Retaining base and intermediate checkpoints makes it possible to compare the adaptation trajectory rather than selecting only the final artifact.

Code 
history={"step_100":{"target":.58,"retained":.71},"step_500":{"target":.66,"retained":.69},"step_900":{"target":.65,"retained":.62}}
for step,metrics in history.items(): print(step,metrics)

Level 4 - Audit and selection

Choose an adaptation method against a declared constraint

An adaptation plan should specify the base checkpoint, task, data provenance, target modules or full parameter scope, rank and scaling where relevant, quantisation and precision, maximum length, optimiser settings, token budget, checkpoint policy, merge status, and serving route. It should report target-task results and a retained-task suite under the same prompt template and decoding policy.

The method should not be selected solely because it is cheaper or because it reaches the lowest training loss. A full update may be necessary for a target distribution; a low-rank update may be sufficient and operationally preferable. Both conclusions require evidence under the specified task and deployment conditions.

Regression tests should include the base interface

Adaptation can change outputs for prompts outside the fine-tuning corpus. Retained tests should include general instruction responses, domain tasks that must remain available, formatting or tool contracts, and safety-sensitive inputs where relevant. Tests must specify whether the adapter is active and which system template is used. Comparing a base checkpoint without its standard template to an adapter checkpoint with a richer interface would not isolate the update.

Code 
results={"target":{"base":.48,"adapter":.67},"retained":{"base":.72,"adapter":.70}}
for suite,scores in results.items(): print(suite,scores)

Common misconceptions

  • PEFT changes only a few values, so it cannot cause a large behavioural change. Small modules can substantially change the effective function.
  • An adapter can be used with any model of the same size. It requires the compatible base and architecture contract.
  • Freezing the base eliminates training memory demands. Base weights and activations remain.
  • Merged and separate adapters always give the same result without qualification. Scaling, dtype, and correct base identity are required.
  • A lower training loss identifies the best adaptation method. Target, retained, and systems constraints require separate evidence.

Summary

Full fine-tuning updates selected base parameters, while parameter-efficient methods train smaller updates over a frozen checkpoint. LoRA represents one such update as a low-rank matrix product. The choice changes trainable parameter count, optimiser state, checkpoint storage, and serving design, but it does not remove the need for task data, compatibility metadata, or regression evaluation.

Chapter 32 examines lower-precision weights and activations as a separate efficiency and accuracy trade-off.

The method should not be selected solely because it is cheaper or because it reaches the lowest training loss. A full update may be necessary for a target distribution; a low-rank update may be sufficient and operationally preferable. Both conclusions require evidence under the specified task and deployment conditions.

### Regression tests should include the base interface

Adaptation can change outputs for prompts outside the fine-tuning corpus. Retained tests should include general instruction responses, domain tasks that must remain available, formatting or tool contracts, and safety-sensitive inputs where relevant. Tests must specify whether the adapter is active and which system template is used. Comparing a base checkpoint without its standard template to an adapter checkpoint with a richer interface would not isolate the update.

```{python}
results={"target":{"base":.48,"adapter":.67},"retained":{"base":.72,"adapter":.70}}
for suite,scores in results.items(): print(suite,scores)
```

## Common misconceptions

- **PEFT changes only a few values, so it cannot cause a large behavioural change.** Small modules can substantially change the effective function.
- **An adapter can be used with any model of the same size.** It requires the compatible base and architecture contract.
- **Freezing the base eliminates training memory demands.** Base weights and activations remain.
- **Merged and separate adapters always give the same result without qualification.** Scaling, dtype, and correct base identity are required.
- **A lower training loss identifies the best adaptation method.** Target, retained, and systems constraints require separate evidence.

## Summary

Full fine-tuning updates selected base parameters, while parameter-efficient methods train smaller updates over a frozen checkpoint. LoRA represents one such update as a low-rank matrix product. The choice changes trainable parameter count, optimiser state, checkpoint storage, and serving design, but it does not remove the need for task data, compatibility metadata, or regression evaluation.
