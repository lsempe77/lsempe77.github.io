Outcomes, processes, verifiers, robustness, and inference-time cost

Chapter orientation

Why this chapter matters

Chapter 35 defined reasoning systems through additional computation, search, decomposition, and verification. An evaluation must now determine whether those mechanisms improve the intended task and at what cost. A correct final answer is useful evidence, but it cannot show whether a visible trace was faithful, whether a verifier was valid, whether the gain survives prompt variation, or whether more inference-time compute is worth its latency and expense.

Reasoning evaluation should therefore retain outcome, process, and systems measures. The relevant criterion depends on the task. Exact arithmetic permits an exact verifier; open-ended planning requires another source of evidence. Chapter 37 will compare accuracy against inference-time computation, using the measurement contract established here.

Learning objectives

By the end of this chapter, you should be able to:

  • distinguish outcome, process, verifier, robustness, and systems evaluation;
  • define an exact verifier and state its scope;
  • calculate outcome accuracy and verifier precision or recall on a toy set;
  • explain why a plausible trace is not evidence of faithfulness;
  • design prompt- and problem-variant robustness tests;
  • report accuracy together with samples, tokens, calls, latency, and cost; and
  • build a trace that separates candidate, verifier, selection, and final-answer errors.

Running task

The running task has a checkable answer. The system generates candidate solutions, applies a verifier, and selects one result. This permits separate measurements of candidate coverage, verifier behaviour, and final accuracy.

Verifier. A procedure that evaluates a candidate answer or process against a stated rule. Its usefulness depends on coverage, false acceptance, false rejection, abstention, and the decision made from its output.

False acceptance and false rejection. False acceptance occurs when a verifier approves an incorrect candidate. False rejection occurs when it rejects a correct one. Their costs depend on the task and determine whether a threshold or abstention route is appropriate.

Level 1 - Intuition

A final answer is necessary but incomplete evidence

For a task with one exact answer, outcome accuracy asks whether the selected result is correct. This is often the primary metric. It does not show whether the system used a valid method, whether a visible rationale was accurate, whether a tool call succeeded, or whether the same result would survive a modest change in wording.

A reasoning system may produce a correct answer through a lucky candidate, a memorised pattern, an external tool, or a verified search process. These mechanisms have different implications for generalisation and cost. Evaluation should not claim more than the measure supports.

Code 
outcomes=np.array([1,1,0,1,1,0,1,1])
print("outcome accuracy:",outcomes.mean(),"items:",len(outcomes))
outcome accuracy: 0.75 items: 8

Outcome measures need a denominator and an error record

Accuracy is the proportion of scored items for which the selected answer meets the stated criterion. It is only interpretable with its denominator: the task version, number of items, inclusion and exclusion rules, answer normalisation, and treatment of abstentions, timeouts, and tool failures. A system that abstains on unverified cases can appear more accurate if those cases are removed from the denominator. Report coverage alongside accuracy, and state whether an abstention is counted as incorrect, deferred, or outside the task.

Aggregate accuracy also compresses different errors. A candidate generator may never produce a valid answer; a verifier may reject the valid candidate; a selector may choose an inferior accepted candidate; an answer parser may score a correct response as wrong. Retaining these boundaries identifies which component changed after a revision. It also prevents a later chapter from interpreting an accuracy gain as evidence that the generator improved when the gain came from a more permissive answer parser.

Process text and process evidence are different

A visible chain of steps can be checked for local arithmetic or logical consistency. It may still omit the operation that determined the answer, contain a post-hoc explanation, or lead to a different answer after a small intervention. Process evaluation is useful when steps are observable and a task supplies criteria for them. It should not be treated as a general window into latent computation.

Level 2 - Verifiers and metrics

A verifier has a defined acceptance condition

An exact verifier can check a numeric answer, proof syntax, executable code output, a formal constraint, or a known solution. Its value comes from a clearly specified condition. A verifier can be wrong, incomplete, vulnerable to formatting, or unable to assess the property that matters. A code test suite may accept an implementation that fails an untested case; a symbolic checker may reject a correct answer in an unsupported form.

Code 
def exact_verifier(candidate,answer):
    return candidate==answer
print([exact_verifier(x,12) for x in [12,11,12,13]])
[True, False, True, False]

Verifier evaluation itself needs labelled cases. Precision asks how often accepted candidates are actually correct; recall asks how often correct candidates are accepted. A selector built on a low-precision verifier can choose attractive errors. A low-recall verifier can discard valid solutions and flatten the gain from candidate generation.

Code 
accepted=np.array([1,1,1,0]); actually_correct=np.array([1,0,1,1])
precision=(accepted & actually_correct).sum()/accepted.sum()
recall=(accepted & actually_correct).sum()/actually_correct.sum()
print("verifier precision:",round(precision,2),"recall:",round(recall,2))
verifier precision: 0.67 recall: 0.67

Candidate coverage, verifier quality, and selection quality are separate quantities

For a multi-candidate system, candidate coverage asks whether at least one generated candidate is correct. Verifier precision and recall ask whether the verifier classifies individual candidates accurately. Selection accuracy asks whether the final policy chooses a correct candidate from the candidates available. These measures identify different ceilings. Sampling cannot rescue a task when coverage remains low; a highly accurate verifier cannot help if no valid candidate is generated; a selector can still fail when several accepted candidates disagree.

Report the measures on the same items and candidate sets. If a verifier is evaluated only on generated candidates, its score may differ from its score on deliberately constructed hard negatives or different answer formats. The difference is useful: it describes the verifier’s operating distribution. Evaluation work on language models treats performance as conditional on the scenario, metric, and slice being measured, rather than as a single property of a model (Liang et al. 2022).

Level 3 - Robustness and cost

Robustness tests vary a declared factor

Reasoning claims should be tested under controlled variants: paraphrase the prompt while preserving the answer, alter irrelevant numbers or names, move evidence position, change the order of answer options, or generate new instances from a problem family. The purpose is to identify whether performance depends on surface cues rather than the relation the task is intended to measure.

Code 
variants={"original":1,"paraphrase":1,"renamed variables":0,"reordered options":0}
print("variant outcomes:",variants)
variant outcomes: {'original': 1, 'paraphrase': 1, 'renamed variables': 0, 'reordered options': 0}

Robustness does not mean invariance to every transformation. A wording change can legitimately alter the problem. The evaluation must state which property is preserved and how variants were built. It should also avoid constructing variants after viewing the model’s failures in a way that turns the test into an unreported development set.

The unit of analysis should remain visible. Report the original and each variant as paired outcomes, rather than pooling them immediately into one score. A system that succeeds on the original item and fails whenever variable names change has a different failure pattern from one that fails randomly across variants, even when their pooled accuracy is the same. Paired records also show whether candidate generation, verification, or selection caused the difference.

Contamination is a provenance question

Benchmark exposure can inflate an outcome score without showing that a system solves new instances. The relevant question is not whether an item appears verbatim in a public dataset alone. It is whether the training data, instruction data, demonstrations, retrieval index, prompt template, or evaluation-development process supplied information that makes the test easier. A reasoning benchmark can also become a development target through repeated prompting and manual inspection, even if the model checkpoint was trained earlier.

Record the dataset version, item source, generation procedure, public availability date, benchmark access policy, and any overlap search or decontamination rule. When a task family permits it, use newly generated or held-out instances and keep the generator and answer key separate from the system-development loop. Established broad benchmarks demonstrate the value of specifying task categories and scoring conventions, but their scores remain tied to the particular item collection and answer format (Hendrycks et al. 2021). A contamination check cannot prove absence of all exposure; it can make the remaining uncertainty visible.

Code 
variants=["original","paraphrase","renamed\nvariables","reordered\noptions"]
candidate_acc=[.82,.79,.61,.67]; selected_acc=[.88,.83,.64,.70]
x=np.arange(len(variants)); fig,ax=plt.subplots(figsize=(7.4,4))

Accuracy must be paired with computation

If a reasoning system samples ten candidates and calls a verifier ten times, its accuracy cannot be compared fairly with a one-pass answer without reporting the additional tokens, calls, latency, and cost. The relationship may be nonlinear: one extra sample can help substantially, while later samples add little. Chapter 37 will estimate such curves; this chapter establishes the shared denominator.

Cost records also need a decision rule. Mean latency can conceal a long tail caused by retries, tool calls, or a search budget reached only for difficult prompts. State whether calls were parallel, whether failed calls count, the hardware or service configuration, and whether cost includes verification. These choices determine what a reported token or latency budget means in deployment.

Comparisons also need uncertainty appropriate to the evaluation unit. When two systems answer the same items, retain their paired outcomes and report how many items changed from wrong to correct and from correct to wrong. A small average difference can be driven by a few cases, especially on a short benchmark or a rare but costly slice. Confidence intervals or resampling summaries can describe sampling uncertainty, but they do not repair an unrepresentative task set or an undeclared change in prompt policy.

Open-ended tasks require a scoring protocol, not an implied exact answer

Some reasoning applications produce plans, explanations, or recommendations for which there is no single reference string. Evaluation then needs a rubric that states the required facts, constraints, source use, prohibited content, and treatment of uncertainty. Human assessment can judge properties that an exact verifier cannot, but it introduces assessor training, disagreement, order effects, and cost. Model-based judging adds another model with its own prompt, calibration, and failure modes.

The protocol should specify who scores which outputs, whether assessors are blinded to system identity, how disagreements are resolved, and which cases require expert review. A rubric score should be reported by criterion and, where possible, alongside concrete error categories. This does not make an open-ended task exact. It permits claims about the property that was actually assessed and leaves the unassessed properties outside the conclusion.

Level 4 - Audit and interpretation

Faithfulness requires an intervention claim

To claim that a visible trace explains an answer, an evaluation needs more than a correlation between plausible steps and correct answers. Interventions can alter, remove, reorder, or replace parts of the trace and test whether the answer changes in the predicted way. These tests are difficult because a model may regenerate a different trace, rely on hidden state, or answer from a shortcut. A negative result should be reported as a limit rather than repaired with a more persuasive explanation.

Code 
trace_test={"original_answer":12,"altered_trace_answer":12,"expected_change":True}
print("trace intervention supports claim:",trace_test["altered_trace_answer"]!=trace_test["original_answer"])
trace intervention supports claim: False

A reasoning evaluation record joins components

The audit should retain task generator or dataset version, answer key or verifier, prompt and template, checkpoint, candidate-generation policy, samples, selection rule, tool and verifier versions, visible-trace policy, token and call counts, latency, outcome scoring, robustness variants, contamination checks, and error categories. It should record whether an item was solved directly, through a verifier, or through a tool. This is the minimum needed to interpret an apparent reasoning gain.

Evaluation should also distinguish a planned test from a diagnostic added after observing errors. Diagnostic slices are often useful, especially when a failure points to a specific parser, tool, or prompt condition. They should not be folded silently into a confirmatory headline score. Keep a development record, freeze the evaluation policy for the final comparison, and state which analyses were exploratory. The resulting account is less tidy than one number, but it permits another evaluator to reproduce the decision boundary.

Code 
record={"task":"verifiable problems","generator":"v2","samples":8,"verifier":"exact-v1","selector":"first accepted","tokens":1440,"robustness":"paraphrase set"}
assert {"task","samples","verifier","selector","tokens"} <= set(record)
print("reasoning evaluation record complete")
reasoning evaluation record complete

Common misconceptions

  • A correct answer proves a correct reasoning process. It does not identify the route that produced the answer.
  • A verifier is objective by definition. It has coverage, parsing, and implementation limits.
  • A plausible rationale is a faithful explanation. Faithfulness requires an intervention or another causal test.
  • More samples can be compared without reporting cost. Candidate count, tokens, calls, and latency change the system.
  • Prompt robustness means invariant outputs under every rewording. Variants need a declared preserved property.
  • A reasoning benchmark rules out contamination. Development and training exposure still require checks.

Summary

Reasoning evaluation needs outcome metrics, verifier diagnostics, robustness tests, faithfulness limits, and inference-time resource records. No single metric establishes all of these properties. A system should be evaluated at its candidate, verifier, selection, and final-answer boundaries under a declared task distribution.

Chapter 37 uses this measurement framework to test when sampling, voting, and verification improve accuracy enough to justify their additional computation.

Looking ahead

Reasoning evaluation makes the cost of additional computation observable. Chapter 37 examines how a fixed model can allocate that computation across candidates, verification, and search.

```{python}
fig,ax=plt.subplots(figsize=(5,4)); im=ax.imshow(matrix,cmap="Blues"); ax.set_xticks([0,1],["actually correct","actually incorrect"]); ax.set_yticks([0,1],["accepted","rejected"])
for i in range(2):
    for j in range(2): ax.text(j,i,str(matrix[i,j]),ha="center",va="center",fontsize=14)
ax.set_title("Verifier confusion matrix (illustrative)"); plt.tight_layout(); plt.show()
```

### Candidate coverage, verifier quality, and selection quality are separate quantities

For a multi-candidate system, candidate coverage asks whether at least one generated candidate is correct. Verifier precision and recall ask whether the verifier classifies individual candidates accurately. Selection accuracy asks whether the final policy chooses a correct candidate from the candidates available. These measures identify different ceilings. Sampling cannot rescue a task when coverage remains low; a highly accurate verifier cannot help if no valid candidate is generated; a selector can still fail when several accepted candidates disagree.

Report the measures on the same items and candidate sets. If a verifier is evaluated only on generated candidates, its score may differ from its score on deliberately constructed hard negatives or different answer formats. The difference is useful: it describes the verifier's operating distribution. Evaluation work on language models treats performance as conditional on the scenario, metric, and slice being measured, rather than as a single property of a model [@liang2022holistic].

## Level 3 - Robustness and cost

### Robustness tests vary a declared factor

Reasoning claims should be tested under controlled variants: paraphrase the prompt while preserving the answer, alter irrelevant numbers or names, move evidence position, change the order of answer options, or generate new instances from a problem family. The purpose is to identify whether performance depends on surface cues rather than the relation the task is intended to measure.

```{python}
variants={"original":1,"paraphrase":1,"renamed variables":0,"reordered options":0}
print("variant outcomes:",variants)
```

Robustness does not mean invariance to every transformation. A wording change can legitimately alter the problem. The evaluation must state which property is preserved and how variants were built. It should also avoid constructing variants after viewing the model's failures in a way that turns the test into an unreported development set.

The unit of analysis should remain visible. Report the original and each variant as paired outcomes, rather than pooling them immediately into one score. A system that succeeds on the original item and fails whenever variable names change has a different failure pattern from one that fails randomly across variants, even when their pooled accuracy is the same. Paired records also show whether candidate generation, verification, or selection caused the difference.

### Contamination is a provenance question

Benchmark exposure can inflate an outcome score without showing that a system solves new instances. The relevant question is not whether an item appears verbatim in a public dataset alone. It is whether the training data, instruction data, demonstrations, retrieval index, prompt template, or evaluation-development process supplied information that makes the test easier. A reasoning benchmark can also become a development target through repeated prompting and manual inspection, even if the model checkpoint was trained earlier.

Record the dataset version, item source, generation procedure, public availability date, benchmark access policy, and any overlap search or decontamination rule. When a task family permits it, use newly generated or held-out instances and keep the generator and answer key separate from the system-development loop. Established broad benchmarks demonstrate the value of specifying task categories and scoring conventions, but their scores remain tied to the particular item collection and answer format [@hendrycks2021measuring]. A contamination check cannot prove absence of all exposure; it can make the remaining uncertainty visible.

```{python}
#| label: fig-robustness-slices
#| fig-cap: "Paired robustness results show whether reasoning-system failures concentrate in a declared prompt or problem variant rather than only changing the pooled score."
#| fig-alt: "A grouped bar chart compares original, paraphrased, renamed-variable, and reordered-option accuracy for candidate generation and selected answers."
variants=["original","paraphrase","renamed\nvariables","reordered\noptions"]
candidate_acc=[.82,.79,.61,.67]; selected_acc=[.88,.83,.64,.70]
x=np.arange(len(variants)); fig,ax=plt.subplots(figsize=(7.4,4))
ax.bar(x-.18,candidate_acc,.36,label="candidate coverage",color=teal)
ax.bar(x+.18,selected_acc,.36,label="selected-answer accuracy",color=purple)
ax.set_xticks(x,variants); ax.set_ylim(0,1); ax.set_ylabel("accuracy")
ax.legend(); ax.set_title("Illustrative paired robustness slices")
plt.tight_layout(); plt.show()
```

### Accuracy must be paired with computation

If a reasoning system samples ten candidates and calls a verifier ten times, its accuracy cannot be compared fairly with a one-pass answer without reporting the additional tokens, calls, latency, and cost. The relationship may be nonlinear: one extra sample can help substantially, while later samples add little. Chapter 37 will estimate such curves; this chapter establishes the shared denominator.

Cost records also need a decision rule. Mean latency can conceal a long tail caused by retries, tool calls, or a search budget reached only for difficult prompts. State whether calls were parallel, whether failed calls count, the hardware or service configuration, and whether cost includes verification. These choices determine what a reported token or latency budget means in deployment.

Comparisons also need uncertainty appropriate to the evaluation unit. When two systems answer the same items, retain their paired outcomes and report how many items changed from wrong to correct and from correct to wrong. A small average difference can be driven by a few cases, especially on a short benchmark or a rare but costly slice. Confidence intervals or resampling summaries can describe sampling uncertainty, but they do not repair an unrepresentative task set or an undeclared change in prompt policy.

```{python}
records=[{"n":1,"accuracy":.54,"tokens":180,"latency":.4},{"n":4,"accuracy":.68,"tokens":720,"latency":1.7},{"n":8,"accuracy":.72,"tokens":1440,"latency":3.3}]
for row in records: print(row)
```

### Open-ended tasks require a scoring protocol, not an implied exact answer

Some reasoning applications produce plans, explanations, or recommendations for which there is no single reference string. Evaluation then needs a rubric that states the required facts, constraints, source use, prohibited content, and treatment of uncertainty. Human assessment can judge properties that an exact verifier cannot, but it introduces assessor training, disagreement, order effects, and cost. Model-based judging adds another model with its own prompt, calibration, and failure modes.

The protocol should specify who scores which outputs, whether assessors are blinded to system identity, how disagreements are resolved, and which cases require expert review. A rubric score should be reported by criterion and, where possible, alongside concrete error categories. This does not make an open-ended task exact. It permits claims about the property that was actually assessed and leaves the unassessed properties outside the conclusion.

## Level 4 - Audit and interpretation

### Faithfulness requires an intervention claim

To claim that a visible trace explains an answer, an evaluation needs more than a correlation between plausible steps and correct answers. Interventions can alter, remove, reorder, or replace parts of the trace and test whether the answer changes in the predicted way. These tests are difficult because a model may regenerate a different trace, rely on hidden state, or answer from a shortcut. A negative result should be reported as a limit rather than repaired with a more persuasive explanation.

```{python}
trace_test={"original_answer":12,"altered_trace_answer":12,"expected_change":True}
print("trace intervention supports claim:",trace_test["altered_trace_answer"]!=trace_test["original_answer"])
```

### A reasoning evaluation record joins components

The audit should retain task generator or dataset version, answer key or verifier, prompt and template, checkpoint, candidate-generation policy, samples, selection rule, tool and verifier versions, visible-trace policy, token and call counts, latency, outcome scoring, robustness variants, contamination checks, and error categories. It should record whether an item was solved directly, through a verifier, or through a tool. This is the minimum needed to interpret an apparent reasoning gain.

Evaluation should also distinguish a planned test from a diagnostic added after observing errors. Diagnostic slices are often useful, especially when a failure points to a specific parser, tool, or prompt condition. They should not be folded silently into a confirmatory headline score. Keep a development record, freeze the evaluation policy for the final comparison, and state which analyses were exploratory. The resulting account is less tidy than one number, but it permits another evaluator to reproduce the decision boundary.

```{python}
record={"task":"verifiable problems","generator":"v2","samples":8,"verifier":"exact-v1","selector":"first accepted","tokens":1440,"robustness":"paraphrase set"}
assert {"task","samples","verifier","selector","tokens"} <= set(record)
print("reasoning evaluation record complete")
```

## Common misconceptions

- **A correct answer proves a correct reasoning process.** It does not identify the route that produced the answer.
- **A verifier is objective by definition.** It has coverage, parsing, and implementation limits.
- **A plausible rationale is a faithful explanation.** Faithfulness requires an intervention or another causal test.
- **More samples can be compared without reporting cost.** Candidate count, tokens, calls, and latency change the system.
- **Prompt robustness means invariant outputs under every rewording.** Variants need a declared preserved property.
- **A reasoning benchmark rules out contamination.** Development and training exposure still require checks.

## Summary

Reasoning evaluation needs outcome metrics, verifier diagnostics, robustness tests, faithfulness limits, and inference-time resource records. No single metric establishes all of these properties. A system should be evaluated at its candidate, verifier, selection, and final-answer boundaries under a declared task distribution.
