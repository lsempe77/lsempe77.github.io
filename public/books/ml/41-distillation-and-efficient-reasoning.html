Transferring behaviour from slower teachers to cheaper students

Chapter orientation

Why this chapter matters

A reasoning system can improve accuracy by sampling, searching, verifying, or using a larger model, but these procedures can be too slow or costly for every request. Distillation trains a student to imitate selected teacher outputs or distributions. In reasoning settings, the teacher may provide answers, checked solution traces, candidate rankings, or a routing policy that decides when extra computation is warranted.

Distillation transfers observed behaviour under a data and interface distribution. It does not prove that the student has acquired the teacher’s internal computation, and it can transfer errors, style, or reward-hacking patterns. This chapter treats teacher generation, selection, student training, and efficiency evaluation as one pipeline.

Learning objectives

By the end of this chapter, you should be able to:

  • distinguish teacher, student, distillation dataset, and deployment policy;
  • explain answer, trace, and logit distillation;
  • identify teacher-selection and trace-quality risks;
  • compare teacher and student on accuracy, latency, tokens, and cost;
  • describe adaptive routing between a student and teacher; and
  • specify a distillation audit record.

Running system

The teacher uses a larger inference budget to generate and verify candidates. Accepted outputs become a dataset for a smaller student, which is then evaluated without assuming that imitation loss measures reasoning quality.

Level 1 - Intuition

A teacher can spend more computation than a student

The teacher may be larger, use more samples, call a verifier, or search longer trajectories. The student is trained to produce a useful answer with fewer parameters, shorter outputs, or one pass. The intended gain is a better accuracy–latency–cost frontier, not necessarily identical outputs.

Code 
systems={"teacher":{"accuracy":.78,"tokens":1800,"latency":4.1},"student":{"accuracy":.69,"tokens":260,"latency":.5}}
for name,metrics in systems.items(): print(name,metrics)

Distillation targets can have different information

Answer distillation trains on a final selected answer. Trace distillation includes intermediate text. Logit distillation matches a teacher distribution over tokens. Each target changes what the student can imitate. A long teacher trace can contain useful decomposition, unnecessary prose, or an error that happened not to affect the final answer. Selection and filtering are therefore part of the dataset construction.

A target needs provenance as well as content

For every retained target, record which teacher version generated it, the prompt and context supplied to the teacher, generation settings, tools or retrieval sources used, selection rule, verification result, and date. A student trained on an answer produced with a private retrieval index or an unavailable tool may learn a response pattern that cannot be supported at deployment. A student trained on public sources may still need a record of the source boundary when the task asks for citations or time-sensitive facts.

Provenance also separates teacher quality from data leakage. If a teacher response was generated after exposure to an evaluation item or with access to its answer key, it should not become a target for a student evaluated on that item family. Classical distillation transfers a teacher signal through a defined training objective; the signal is only interpretable when its source distribution and interface are known (Hinton, Vinyals, and Dean 2015).

Level 2 - Data and training mechanics

Teacher filtering determines what is learned

Teacher outputs can be retained only when an exact verifier accepts, when several samples agree, when a human reviewer approves, or when a learned score crosses a threshold. Each policy changes coverage. Filtering only easy verified examples can create a clean but narrow student dataset; retaining unverified traces can transfer errors and unsupported claims.

Code 
teacher_outputs=[{"answer":12,"verified":True},{"answer":13,"verified":False},{"answer":12,"verified":True}]
targets=[row for row in teacher_outputs if row["verified"]]
print("retained targets:",targets)

The student loss can be ordinary next-token cross-entropy over selected targets, a divergence from teacher logits, or a mixture with original data. The data mixture, target mask, template, tokenizer, and maximum length remain the training contract from Chapters 25 and 29.

Target selection is a substantive modelling choice. A verified final answer may be appropriate when the deployment task only needs a final answer. A trace may be retained when intermediate steps are needed for checking or user-facing explanation, but it should be filtered separately from the answer. A teacher can produce a correct answer with an unsupported trace, or a useful trace that is too long for the student’s context and serving budget. Store answer and trace acceptance decisions separately so that later evaluation can identify what the student was trained to imitate.

Filtering changes coverage and the student task distribution

Filtering is often described as quality control, but it also changes which problems the student sees. Exact verification can concentrate targets in tasks with easy-to-check answers. A length limit can remove the multi-step cases that motivated the teacher. Deduplication can reduce repeated templates while also removing an important high-frequency deployment pattern. Report retention rates by task type, difficulty proxy, target length, verifier result, and rejection reason.

The student dataset may combine teacher targets with original instruction data, human-written examples, or tasks designed to preserve general capabilities. The mixture weights define a trade-off between imitation of the teacher and retention of behaviours outside the teacher-target distribution. Changing that mixture changes the effective objective. Hold the evaluation suite fixed and report student outcomes by the sources of the training mixture rather than treating a single loss value as evidence of general transfer.

Target diversity needs its own review. Multiple teacher answers can encode alternative valid strategies, but a dataset dominated by one preferred trace style can narrow the student’s outputs and make it brittle when a task requires another route. Group targets by task, answer form, length, tool use, and verifier outcome; then inspect whether the retained distribution reflects deployment demand or only the teacher’s easiest successes. Diversity is not a goal in itself. It is evidence about the range of behaviour the student has an opportunity to learn.

Evaluate the student both on target-like held-out tasks and on tasks that deliberately require a different valid answer form. The first tests transfer fidelity; the second tests whether filtering produced an unnecessarily narrow response policy.

Report both results before choosing a target-filtering policy for deployment.

Level 3 - Efficiency and routing

Efficiency needs a matched comparison

Compare teacher and student under the same task set, prompt template, decoding rule, context policy, and scoring criterion. Report accuracy, calibration or abstention where relevant, generated tokens, model calls, peak memory, latency distribution, throughput, and cost. A student that copies short answers may appear efficient while failing tasks that need a longer explanation or tool call.

Efficiency claims need a break-even boundary

Teacher generation is an upfront cost that can be amortised only over a stated number of student-served requests. Let teacher-data generation cost be (C_T), student training cost be (C_S), teacher serving cost per request be (c_T), and student serving cost be (c_S). The student becomes cheaper than teacher-only serving after enough requests that the saved per-request cost exceeds (C_T+C_S), subject to the quality constraint that motivated distillation. The calculation changes when a routed system still sends some requests to the teacher.

Memory footprint and throughput can matter separately from single-request latency. A smaller student may permit larger batches or a cheaper device, but a long student trace can erase the expected token saving. Report the serving configuration, batch policy, precision, context length, caching policy, and quality threshold used for the comparison. Chapter 32 explains some execution mechanisms; this chapter uses them only to define a matched teacher–student efficiency claim.

Routing can reserve the teacher for difficult inputs

A deployment can use a student for routine requests and route uncertain, high-stakes, or verifier-failing requests to a slower teacher. The routing signal must be available before the final answer and evaluated by route. A student confidence score can be miscalibrated; a failed verifier may be a verifier limitation rather than evidence of a difficult problem.

Routing has false positives and false negatives. An unnecessary teacher escalation consumes the budget without improving the answer. A missed escalation leaves a difficult input with the student. Evaluate routing on a held-out set by reporting the fraction routed, student-only accuracy, teacher-routed accuracy, and the counterfactual performance of the alternative route where it can be obtained. The threshold is a deployment decision that trades expected error against latency and cost.

Code 
uncertainty=np.array([.1,.7,.3]); routes=np.where(uncertainty>.5,"teacher","student")
print(routes)

Routing needs abstention, fallback, and drift rules

The routing policy should specify what happens when its uncertainty signal is unavailable, the student output cannot be parsed, the teacher is unavailable, or the request falls outside the routing model’s intended domain. A system can abstain, use a conservative teacher route, return a bounded student answer, or request clarification. These choices change both error and cost and should be evaluated as policy branches rather than handled silently.

Routing also changes over time when the request distribution, student version, teacher version, or verifier changes. Monitor the routed fraction, escalation reasons, teacher benefit on a sampled counterfactual set, and route-specific failure categories. A rising escalation rate may indicate that the student no longer covers the workload; a falling rate may reflect a threshold change rather than a better student. Keep the threshold and routing model version in the deployment record.

Level 4 - Audit and limits

Distillation can transmit errors and incentives

The teacher may be wrong, exploit a reward, cite unavailable sources, or produce a plausible trace that is not faithful. A verified answer target can still hide an invalid process; a trace target can teach stylistic reasoning without improved outcomes. Audit teacher error categories, filtering exclusions, data overlap with evaluations, and student regressions on inputs unlike the teacher dataset.

Efficiency claims need the whole pipeline boundary. Teacher-data generation can be expensive even if the student is cheap at serving time. Report whether the claimed saving is per request, after amortising teacher generation over a stated number of requests, or at a fixed quality threshold. A routed system also needs a route-level error record: which inputs were escalated, why, and whether the teacher actually improved the result.

Teacher–student disagreement identifies what was and was not transferred

Evaluate cases where teacher and student disagree, including teacher-correct/student-wrong, student-correct/teacher-wrong, both-wrong, and answers that differ only in format or trace. This is more informative than an average imitation loss. A student may improve on a narrow deployment slice by avoiding an expensive teacher habit, while losing performance on tasks that require the teacher’s search or tool use. These outcomes need task scoring, not a presumption that the teacher is always the gold standard.

Regression tests should cover inputs outside the teacher-target distribution: different lengths, formats, domains, languages where relevant, tool availability, and adversarial or malformed requests. The objective is to identify the scope of transfer and the system conditions under which the student should defer, not to claim that a student contains a compressed copy of all teacher capabilities.

Code 
record={"teacher":"search-v2","selection":"exact verifier","target":"answer only","student":"small-v1","routing":"uncertainty threshold","evaluation":"held-out"}
assert {"teacher","selection","target","student","evaluation"} <= set(record)
print("distillation record complete")

The audit record should include the cost of target generation and filtering, data retention by reason, student training configuration, route policy and threshold, and the model versions used for every comparison. If the teacher is updated, regenerate or version the target set rather than treating new teacher outputs as interchangeable with the old dataset. These fields permit a later evaluator to separate a student-model change from a new teacher, a changed filter, or a change in the request mix.

Common misconceptions

  • A distilled student contains the teacher’s reasoning procedure. It learns from selected outputs under a limited distribution.
  • Verified targets make student evaluation unnecessary. The student can fail to generalise or change formatting and stopping behaviour.
  • Shorter traces always mean efficient reasoning. They can omit needed computation or explanation.
  • Routing removes the need to evaluate the student. Each route and routing error requires measurement.
  • A student matching teacher loss has matched task capability. Outcome and systems evaluation remain necessary.

Summary

Distillation transfers selected teacher behaviour to a student that can be cheaper to deploy. Its result depends on teacher generation, target type, filtering, student training, and routing policy. Evaluate the student and complete system on task outcome, reliability, latency, and cost rather than treating imitation as proof of transferred reasoning.

Looking ahead

Distillation changes the cost and observability of a reasoning system without removing the need to evaluate its resulting behaviour. Chapter 42 brings together the limits of proxy rewards, verifiers, search, evidence, and deployment claims.

## Level 4 - Audit and limits

### Distillation can transmit errors and incentives

The teacher may be wrong, exploit a reward, cite unavailable sources, or produce a plausible trace that is not faithful. A verified answer target can still hide an invalid process; a trace target can teach stylistic reasoning without improved outcomes. Audit teacher error categories, filtering exclusions, data overlap with evaluations, and student regressions on inputs unlike the teacher dataset.

Efficiency claims need the whole pipeline boundary. Teacher-data generation can be expensive even if the student is cheap at serving time. Report whether the claimed saving is per request, after amortising teacher generation over a stated number of requests, or at a fixed quality threshold. A routed system also needs a route-level error record: which inputs were escalated, why, and whether the teacher actually improved the result.

### Teacher–student disagreement identifies what was and was not transferred

Evaluate cases where teacher and student disagree, including teacher-correct/student-wrong, student-correct/teacher-wrong, both-wrong, and answers that differ only in format or trace. This is more informative than an average imitation loss. A student may improve on a narrow deployment slice by avoiding an expensive teacher habit, while losing performance on tasks that require the teacher's search or tool use. These outcomes need task scoring, not a presumption that the teacher is always the gold standard.

Regression tests should cover inputs outside the teacher-target distribution: different lengths, formats, domains, languages where relevant, tool availability, and adversarial or malformed requests. The objective is to identify the scope of transfer and the system conditions under which the student should defer, not to claim that a student contains a compressed copy of all teacher capabilities.

The audit record should include the cost of target generation and filtering, data retention by reason, student training configuration, route policy and threshold, and the model versions used for every comparison. If the teacher is updated, regenerate or version the target set rather than treating new teacher outputs as interchangeable with the old dataset. These fields permit a later evaluator to separate a student-model change from a new teacher, a changed filter, or a change in the request mix.

## Common misconceptions

- **A distilled student contains the teacher's reasoning procedure.** It learns from selected outputs under a limited distribution.
- **Verified targets make student evaluation unnecessary.** The student can fail to generalise or change formatting and stopping behaviour.
- **Shorter traces always mean efficient reasoning.** They can omit needed computation or explanation.
- **Routing removes the need to evaluate the student.** Each route and routing error requires measurement.
- **A student matching teacher loss has matched task capability.** Outcome and systems evaluation remain necessary.

## Summary

Distillation transfers selected teacher behaviour to a student that can be cheaper to deploy. Its result depends on teacher generation, target type, filtering, student training, and routing policy. Evaluate the student and complete system on task outcome, reliability, latency, and cost rather than treating imitation as proof of transferred reasoning.
