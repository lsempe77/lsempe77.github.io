Reward hacking, unreliable traces, verification gaps, and unresolved reasoning claims

Chapter orientation

Why this chapter matters

Part V has described systems that generate more candidates, verify outcomes, revise proposals, search partial states, learn from rewards, and distil slower teachers. These mechanisms can improve defined tasks. They also create stronger incentives to optimise proxies, hide uncertainty, overfit benchmarks, and interpret a visible trace as evidence it does not provide.

This chapter identifies the limits that remain after the mechanisms are specified. The aim is not to dismiss reasoning systems, but to keep claims tied to evidence, task distributions, resource budgets, and known failure modes.

Learning objectives

By the end of this chapter, you should be able to:

  • identify reward-hacking and verifier-gap risks;
  • distinguish answer correctness, process quality, and trace faithfulness;
  • explain why benchmark gains may not generalise;
  • state open questions about hidden computation and process supervision; and
  • write a bounded reasoning-system claim.

Level 1 - Limits follow from the training signal

A proxy can be optimised without solving the intended task

Rewards, learned judges, automatic verifiers, and benchmark metrics are signals. They simplify a broader task into a measurable condition. A policy can improve the signal while exploiting a loophole, selecting an easy subset, or producing an answer that looks appropriate to the evaluator. The more aggressively a system is optimised against a proxy, the more independent evaluation matters.

The relevant question is always which task property the proxy actually observes. An exact arithmetic checker observes a narrow but useful property. A learned judge may observe style, answer format, or agreement with its own training labels in addition to the intended property. A benchmark score observes performance on its item set and interface. The audit should name this measurement boundary before interpreting an optimisation gain.

Proxy audits need deliberate abuse cases

A reward audit should construct cases that satisfy the observable condition while failing the intended task, then test whether the system receives reward or selection preference. For a parser, vary equivalent answer forms, malformed delimiters, and extraneous text. For a source-based response, test irrelevant citations, outdated sources, and claims that cite a source without being entailed by it. For a learned judge, include confident but false answers and unusual but valid answer forms. The purpose is to map the proxy’s known blind spots before a policy is trained aggressively against it.

Record the exploit family, the expected task judgement, the proxy result, and the mitigation or residual risk. A mitigation can close one loophole while opening another or changing the distribution of accepted outputs. The independent test must remain outside the optimisation loop; otherwise the policy can learn the revised test rather than the intended task. This is the same distinction between a verifier’s score and the outcome it is supposed to indicate that motivates verifier-guided evaluation (Cobbe et al. 2021).

Code 
cases=[{"reward":1,"task_success":1,"description":"valid solution"},{"reward":1,"task_success":0,"description":"verifier loophole"}]
for case in cases: print(case)

Level 2 - Trace and verification limits

Visible steps are not a complete account of computation

A natural-language rationale may be useful for checking an arithmetic step or communicating an answer. It can also be incomplete, post-hoc, or selected for readability. Hidden computation cannot be inspected directly by a user. Neither condition justifies an invented explanation. Faithfulness remains an intervention question: does changing the proposed explanatory element change the relevant computation or outcome in the predicted way?

Code 
trace_test={"trace_plausible":True,"answer_correct":False,"faithfulness_established":False}
print(trace_test)

Verification has a parallel limit. Exact verifiers are strong where the specification is complete. Many real tasks have incomplete rules, ambiguous objectives, or evidence that changes over time. A system should state which condition it checked and which it did not.

Verification should therefore be treated as a component with coverage. A program test can establish that a submitted program passes listed cases, not that it satisfies every unstated requirement. A source checker can establish that a citation is present, not that it supports the claim. When the specification is partial, an accepted result should be described as accepted under the stated test, and independent cases should target the most plausible omissions.

A verifier also has false acceptance, false rejection, and abstention behaviour

Coverage is not enough to describe a verifier. A verifier can accept an invalid candidate, reject a valid one, fail to parse an answer, time out, or abstain because the property cannot be checked. These outcomes affect both training and deployment. False acceptance can teach or return an error; false rejection can remove a rare correct candidate from search or distillation; an unrecorded abstention can make an accepted-only accuracy statistic appear stronger than the actual system outcome.

Evaluate the verifier on labelled cases that include its expected operating distribution and likely adversarial or out-of-format cases. Report error rates by task slice and state the policy for unverified candidates: reject, defer, request another candidate, route to review, or return a bounded response. Process-supervision work highlights a related limitation: adding intermediate evaluation creates another judge whose validity requires separate evidence (Lightman et al. 2023).

Level 3 - Evaluation and generalisation

Benchmark performance is conditional evidence

Reasoning benchmarks can be contaminated, public, narrow, or susceptible to prompt and reward optimisation. A high score may establish performance on a well-defined test distribution while leaving open whether the system transfers to new variants, other languages, longer contexts, or tasks without an exact verifier. Refreshing item pools and retaining hidden holdouts help, but they do not replace task-specific deployment evaluation.

Generalisation evidence has layers. A held-out split from the same generator tests one form of interpolation. Paraphrases, changed values, and new templates test declared surface invariances. A new task generator or deployment workflow tests a stronger transfer claim. These designs answer different questions and should not be reported as if they supplied the same evidence. Contamination checks likewise need a documented search procedure, data cutoff, and a decision about items with uncertain exposure.

Benchmark provenance and deployment evidence answer different questions

A benchmark record should identify its item source, generator or collection process, publication date, answer interface, scoring rule, access conditions, and the model-development activities that could have exposed the system to it. These fields do not prove that contamination is absent. They make the exposure claim inspectable and identify which items need replacement or separate reporting. Broad language-model evaluations illustrate why a single aggregate score must be read through its scenarios and measurement choices (Liang et al. 2022).

Deployment evidence begins where the benchmark ends. It records the incoming task distribution, tool availability, user-facing constraints, route or abstention policy, resource budget, and observed failures after release. A model can score well on a static test and still fail because its inputs arrive in a different format, its sources are stale, or a downstream decision requires a property the benchmark did not score. These are not exceptions to evaluation; they define the scope of the system claim.

Generalisation estimates have uncertainty and failure concentration

An observed difference across a benchmark or a controlled variant is an estimate from a finite set of items. Report the number of items, paired outcomes where systems are compared on the same cases, and uncertainty appropriate to the score. More importantly, inspect whether the difference is concentrated in one template, one answer format, one verifier condition, or a small number of high-cost errors. A stable aggregate can conceal a deployment-relevant slice that fails consistently.

New task generators and deployment tests also need versioning. If an evaluation set is refreshed after a model failure, retain the earlier version and mark the change; otherwise later comparisons cannot distinguish a model improvement from an easier or differently composed test. The objective is not an immutable benchmark. It is a record of which evidence supported each system decision at the time it was made.

Level 4 - Open questions and responsible claims

The unresolved questions are empirical

Open questions include how to measure whether a trace is faithful; how to train process supervision without rewarding a style; how to verify open-ended reasoning; how inference-time compute generalises across tasks; how to detect reward hacking before deployment; and how to compare systems with different hidden computation and costs. These questions require experiments with defined interventions and held-out tasks, not labels attached to outputs.

An appropriate concluding claim names the task distribution, the mechanism, the comparison, the resource change, and the remaining uncertainty. For example, a result may show that a fixed candidate-and-verifier procedure improves exact accuracy on held-out problems from one generator at a stated token cost. It does not establish faithful visible reasoning, broad transfer, or a property of hidden computation unless those claims received separate evidence. This is a restriction on interpretation, not a reason to discard a measured result.

Hidden computation changes the evidence available to users and auditors

A system may use internal activations, private tools, hidden tokens, or proprietary retrieval and still be evaluated on observable task outcomes, resources, and interfaces. What cannot be concluded is that a concise visible explanation faithfully reports the inaccessible computation. An organisation that withholds traces should state what record is retained for debugging, what an external evaluator can inspect, which failures can be reconstructed, and which claims remain untestable because the relevant state is unavailable.

This is an accountability boundary. It does not require exposing every intermediate representation or confidential prompt. It does require that the system not substitute a polished rationale for an unavailable audit trail. Task outcomes, verifier decisions, tool-call status, budget exhaustion, and versioned policy changes can be recorded without claiming that they reveal the model’s entire internal process.

Limits require a deployment decision, not only a disclosure

An identified limit should change a system policy where the consequence warrants it. A verifier with poor coverage can trigger abstention or review for the uncovered class. A suspected reward exploit can pause a training update or remove the affected reward version. A trace that is useful for communication but not faithful should be labelled as an explanation or summary rather than evidence of the causal process. A benchmark that no longer reflects the workload should lose its role as the main release criterion.

The decision record should identify the limit, the affected task slice, the monitoring signal, the action threshold, the owner, and the review date. This makes uncertainty operational. It also prevents a general warning about limitations from becoming a reason to leave known high-consequence failures without a response policy.

Version the decision record with the model, verifier, tool, prompt, and deployment configuration it governs. A response policy that was adequate for one system can become invalid when any of those components changes.

Review changes before they reach users, not only after incidents occur.

Open questions require a stated evidential path

Each unresolved question should be converted into an experiment or monitoring obligation. Trace faithfulness requires a defined intervention and predicted outcome. Process supervision requires labelled step data, judge-error analysis, and a comparison with outcome-only feedback. Reward-hacking detection requires held-out abuse cases and independent outcomes. Claims about inference-time scaling require matched budgets, candidate dependence records, and task slices. Claims about general transfer require a new generator or deployment evaluation rather than another score on the same public item pool.

The remaining uncertainty should be recorded when a system is deployed, not deferred to a final caveat. Name the unmeasured property, the evidence that would be needed, the consequence if the property fails, and the decision owner responsible for updating or limiting the system. That record connects the reasoning module to the deployment and safety questions developed in Part VI.

claim={"task":"held-out verified problems","mechanism":"eight samples plus exact verifier","result":"higher accuracy at higher token cost","limit":"does not establish general reasoning"}
print(claim)

Common misconceptions

  • A reasoning trace is a proof of reasoning. It is output that needs its own evaluation.
  • A verifier closes the evaluation problem. It covers only its declared acceptance condition.
  • Reward optimisation solves alignment. It can optimise an incomplete proxy.
  • A benchmark gain is a general capability claim. It is evidence under a measured distribution.
  • Hidden computation removes accountability. Outcomes, resources, and system traces remain evaluable.

Summary

Reasoning systems can improve defined outcomes through search, verification, reward learning, and distillation. Their limits arise from proxy optimisation, incomplete verifiers, unreliable traces, narrow benchmarks, and unobserved computation. Claims should remain tied to the task, mechanism, evaluation, cost, and known gaps.

A suspected reward exploit can pause a training update or remove the affected reward version. A trace that is useful for communication but not faithful should be labelled as an explanation or summary rather than evidence of the causal process. A benchmark that no longer reflects the workload should lose its role as the main release criterion.

The decision record should identify the limit, the affected task slice, the monitoring signal, the action threshold, the owner, and the review date. This makes uncertainty operational. It also prevents a general warning about limitations from becoming a reason to leave known high-consequence failures without a response policy.

Version the decision record with the model, verifier, tool, prompt, and deployment configuration it governs. A response policy that was adequate for one system can become invalid when any of those components changes.

Review changes before they reach users, not only after incidents occur.

### Open questions require a stated evidential path

Each unresolved question should be converted into an experiment or monitoring obligation. Trace faithfulness requires a defined intervention and predicted outcome. Process supervision requires labelled step data, judge-error analysis, and a comparison with outcome-only feedback. Reward-hacking detection requires held-out abuse cases and independent outcomes. Claims about inference-time scaling require matched budgets, candidate dependence records, and task slices. Claims about general transfer require a new generator or deployment evaluation rather than another score on the same public item pool.

The remaining uncertainty should be recorded when a system is deployed, not deferred to a final caveat. Name the unmeasured property, the evidence that would be needed, the consequence if the property fails, and the decision owner responsible for updating or limiting the system. That record connects the reasoning module to the deployment and safety questions developed in Part VI.

## Common misconceptions

- **A reasoning trace is a proof of reasoning.** It is output that needs its own evaluation.
- **A verifier closes the evaluation problem.** It covers only its declared acceptance condition.
- **Reward optimisation solves alignment.** It can optimise an incomplete proxy.
- **A benchmark gain is a general capability claim.** It is evidence under a measured distribution.
- **Hidden computation removes accountability.** Outcomes, resources, and system traces remain evaluable.
