Supervised adaptation from continuation to instruction-following behaviour

Chapter orientation

Why this chapter matters

A base language model predicts continuations of token sequences. It may complete an instruction, continue it, imitate an answer, or produce an unrelated pattern depending on the prompt and its pretraining distribution. Instruction tuning adapts the model on examples formatted as requests and preferred responses so that a defined interface more reliably produces the intended response style.

The optimisation remains token prediction, but the training examples, target mask, conversation template, and evaluation task change. This chapter explains that change without claiming that supervised demonstrations establish factuality, safety, or preference alignment. Chapter 30 examines preference optimisation; Chapter 31 examines full and parameter-efficient task adaptation.

Learning objectives

By the end of this chapter, you should be able to:

  • distinguish base pretraining from supervised instruction tuning;
  • define instruction, context, response, template, and target tokens;
  • explain why loss is normally applied to response tokens rather than the user’s request;
  • identify data quality, diversity, and split risks in demonstration datasets;
  • implement a target mask for a toy chat example;
  • describe catastrophic forgetting and regression evaluation; and
  • specify the metadata needed to reproduce an instruction-tuning run.

Running conversation

The running example has a system instruction, a user request, and an assistant response. The entire formatted conversation is input to a causal model, but only selected assistant tokens contribute to the supervised loss.

Level 1 - Intuition

Demonstrations define a response convention

An instruction-tuning dataset contains demonstrations of an input and a target response. They may include a system message, a user request, documents or tool outputs, and one or more assistant turns. During fine-tuning, the model sees the context and is trained to assign high probability to the demonstrated assistant tokens. Repeated examples establish a convention about when to answer, how to structure an answer, and how to handle specified formats.

This does not convert a model into a database of verified answers. If demonstrations are wrong, incomplete, inconsistent, or narrowly distributed, the model can learn those patterns. A training run can improve compliance with a template while reducing performance on unrelated base-model behaviours. The desired change and the possible regression must both be evaluated.

Code 
conversation=["<system>","Be concise.","<user>","Name a mammal.","<assistant>","A whale is a mammal."]
print("\n".join(conversation))

The template is not decoration

Role markers tell the model which span is an instruction, which span is user-provided context, and where an assistant response should begin. A checkpoint trained with one template may respond poorly when served with another, even if the visible wording is unchanged. The tokenizer, special tokens, whitespace rules, and tool-call fields are all part of this interface.

Level 2 - Supervised mechanics

Context tokens and target tokens have different roles

The user request must be visible so the model can condition on it. It is usually not a target to reproduce. A common loss mask sets labels for system, user, padding, and structural tokens to an ignore value, while keeping labels for assistant response tokens. The causal model still predicts a distribution at every position, but optimisation averages loss only over supervised positions.

Code 
ids=np.array([2,10,11,3,20,21,4,30,31,32,5])
assistant_start=7; pad_label=-100
labels=np.full_like(ids,pad_label)
labels[assistant_start:]=ids[assistant_start:]
print("IDs:   ",ids)
print("labels:",labels)

An off-by-one target mask can train the model to reproduce user text, omit the first assistant token, or include an end marker inconsistently. The model can still show a decreasing scalar loss, so small examples should print formatted tokens and labels before a large run.

Demonstration quality determines what is reinforced

Instruction data may be written by people, collected from existing tasks, generated by another model, or revised through review. Each source can be useful, but each has distinct error and provenance risks. A dataset should record authorship or generation process, licensing and consent conditions, task categories, languages, response length, quality-control rules, and the version of any model used to synthesize examples.

Data diversity is not a count of surface prompts. It concerns the distribution of tasks, ambiguity, formats, languages, safety-sensitive requests, and response behaviours. A dataset containing many paraphrases of one answer style can produce a narrow model interface. Evaluation splits should prevent template duplicates, source leakage, and near-identical instructions from inflating reported generalisation.

Code 
examples={"extraction":1200,"summarisation":850,"coding":400,"multilingual":150}
print("task counts:",examples)
print("counts describe coverage only when task definitions and selection rules are documented")

Level 3 - Adaptation and regression

Fine-tuning changes shared parameters

Full supervised fine-tuning updates model parameters using gradients from the demonstration loss. The new gradients can improve target behaviours while changing probabilities needed for earlier behaviours. This is often called catastrophic forgetting when adaptation materially degrades retained capabilities. The term does not imply that any change is harmful: the question is whether a regression occurs on a predeclared retained-task set.

Code 
before={"instruction":.42,"base_completion":.31,"code":.38}
after={"instruction":.61,"base_completion":.27,"code":.33}
for task in before: print(task,"change",round(after[task]-before[task],2))

The trade-off depends on data size and composition, learning rate, update count, sequence length, parameter scope, regularisation, and the mismatch between pretraining and adaptation tasks. A training report should retain intermediate checkpoints and evaluate both target and retained behaviours. A final checkpoint selected only on instruction loss can conceal a broader regression.

Multi-turn and tool examples create additional boundaries

In a multi-turn conversation, later assistant targets can condition on earlier assistant text. A training pipeline must specify whether it applies loss to every assistant turn, how it masks user and tool spans, and whether it truncates from the beginning or end. Tool-call examples also require a schema and a decision about whether tool results are trusted context, target text, or both.

Code 
roles=["system","user","assistant","tool","assistant"]
supervise=np.array([False,False,True,False,True])
print(list(zip(roles,supervise)))

Dataset mixtures can create instruction conflicts

Instruction datasets often combine short question-answer examples, summarisation, extraction, coding, safety responses, tool use, and multi-turn conversations. The same visible request can be paired with incompatible target styles across sources: one example may answer directly, another may ask a clarifying question, and a third may refuse. A model cannot infer an unstated hierarchy among such demonstrations. The dataset builder must define source weights, conflict rules, and the intended role of system messages or policy examples.

This is also why response length and formatting deserve an audit. A corpus dominated by terse answers can make longer explanations less probable even when they are appropriate. A corpus dominated by verbose templates can produce unnecessary prefacing. These are not properties of “instruction following” in general; they are patterns in the supervised target distribution.

Training loss is an incomplete selection criterion

Response-token cross-entropy measures agreement with held-out demonstration continuations. It can identify overfitting to a declared validation set, but it cannot by itself show that an answer is helpful for a different user, factually supported, secure in a tool environment, or stable under prompt variation. Model selection should combine the validation loss with task-specific target and regression evaluations that were chosen before inspecting the final checkpoint.

The evaluation must also preserve the serving interface. Comparing a base model under a raw completion prompt with a tuned model under a carefully engineered chat template mixes model adaptation and prompting. A fair comparison can report both interfaces, but it should label them separately and make visible any system messages, retrieval context, decoding constraints, or answer extraction rules.

Code 
checkpoints={"step_100":(1.42,.52,.41),"step_500":(1.28,.61,.37),"step_900":(1.22,.60,.31)}
for step,(loss,target,retained) in checkpoints.items():
    print(step,"validation loss",loss,"target score",target,"retained score",retained)

Errors often originate before the response span

An incorrect instruction-tuned output can arise from an ambiguous request, an incompatible template, truncated context, unsupported content in the demonstration data, a target-mask error, decoding choices, or a model distribution that fails despite correct inputs. An audit should retain the formatted token sequence, role boundaries, masked labels, selected output IDs, and evaluation rationale for representative failures. This makes it possible to repair the relevant component rather than adding examples blindly.

For a system that uses tools or retrieved documents, source availability should be part of the error record. An answer can be stylistically compliant while failing to use a supplied source, or it can cite a source that was never available in the context. Instruction tuning alone does not establish grounding behaviour; the task interface and evaluation need to test it.

The supervised objective has a length and balance policy

Assistant-only masking is not sufficient to define a dataset loss. Long responses contribute more supervised tokens than short responses when loss is averaged over valid target tokens. A corpus with a few long explanations can therefore exert more gradient influence than a larger number of brief extraction examples. Sampling weights, example packing, maximum length, truncation, and the loss denominator should be chosen together and recorded.

Truncation is particularly important in multi-turn data. Removing the beginning of a conversation can discard system instructions or the question that makes an assistant answer meaningful. Removing the end can cut the supervised answer and produce incomplete targets. A pipeline needs a declared rule and tests on representative long conversations, including tool results and retrieved context.

Code 
examples={"short extraction":12,"long explanation":180,"tool conversation":95}
total=sum(examples.values())
for name,tokens in examples.items(): print(name,"supervised-token share",round(tokens/total,2))

Level 4 - Audit and interpretation

Evaluate behaviour, not only response overlap

Exact match is useful for extraction and tightly specified outputs. It is insufficient for many instruction tasks where several answers are valid. Evaluations should define the task, input availability, output criterion, scoring procedure, and any human-review protocol. They should compare the base and tuned checkpoints under the same template and decoding policy, then report both improvements and regressions.

The run record must recover the exact interface

An instruction-tuning record needs base checkpoint and tokenizer, template version, role and special-token rules, source and target masks, training examples and provenance, split policy, maximum length and truncation rule, optimiser settings, parameter scope, checkpoints, target and retained evaluations, decoding settings, and known failure cases. This is the minimum needed to distinguish a model change from a prompt-template or evaluation change.

Code 
record={"base":"versioned checkpoint","template":"v3","target_mask":"assistant only","max_length":2048,"evaluation":"target and retained sets"}
assert {"base","template","target_mask","evaluation"} <= set(record)
print("instruction-tuning record complete")

Common misconceptions

  • Instruction tuning replaces the language-model objective. It usually applies the same token loss to a different, masked demonstration distribution.
  • Every token in a chat transcript should be supervised. User and system text are commonly conditioning context, not desired output.
  • A chat template can be changed without retraining. Its role markers and separators alter the input token sequence.
  • More demonstrations automatically give broader instruction following. Coverage, quality, duplication, and task mix determine what is reinforced.
  • Improved instruction scores prove no retained capability declined. Regression tests are required.
  • A compliant response is necessarily a correct response. Format following and factual validity require separate evidence.

Summary

Instruction tuning adapts a base model to role-formatted demonstrations by applying supervised token loss to declared response spans. The template, tokenizer, target mask, data provenance, and loss denominator define the actual adaptation task. A tuned model must be evaluated for both target behaviour and retained capabilities.

Chapter 30 examines how preference data and related objectives compare candidate responses rather than simply reproducing one demonstration.

Looking ahead

Instruction tuning fits stated target responses. Chapter 30 examines learning from a different supervision form: comparisons between alternative responses to the same prompt.

### The run record must recover the exact interface

An instruction-tuning record needs base checkpoint and tokenizer, template version, role and special-token rules, source and target masks, training examples and provenance, split policy, maximum length and truncation rule, optimiser settings, parameter scope, checkpoints, target and retained evaluations, decoding settings, and known failure cases. This is the minimum needed to distinguish a model change from a prompt-template or evaluation change.

```{python}
record={"base":"versioned checkpoint","template":"v3","target_mask":"assistant only","max_length":2048,"evaluation":"target and retained sets"}
assert {"base","template","target_mask","evaluation"} <= set(record)
print("instruction-tuning record complete")
```

## Common misconceptions

- **Instruction tuning replaces the language-model objective.** It usually applies the same token loss to a different, masked demonstration distribution.
- **Every token in a chat transcript should be supervised.** User and system text are commonly conditioning context, not desired output.
- **A chat template can be changed without retraining.** Its role markers and separators alter the input token sequence.
- **More demonstrations automatically give broader instruction following.** Coverage, quality, duplication, and task mix determine what is reinforced.
- **Improved instruction scores prove no retained capability declined.** Regression tests are required.
- **A compliant response is necessarily a correct response.** Format following and factual validity require separate evidence.

## Summary

Instruction tuning adapts a base model to role-formatted demonstrations by applying supervised token loss to declared response spans. The template, tokenizer, target mask, data provenance, and loss denominator define the actual adaptation task. A tuned model must be evaluated for both target behaviour and retained capabilities.
