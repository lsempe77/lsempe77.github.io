Capability, reliability, contamination, and the limits of benchmark scores

Chapter orientation

Why this chapter matters

An LLM evaluation produces evidence about a defined model or system under a defined input distribution, interface, scoring rule, and time. It does not produce a general scalar measure of intelligence, truthfulness, or fitness for every deployment. The same model can score differently after a template change, a decoding change, an index update, a tool change, or a contaminated test item.

This chapter closes Part IV by treating evaluation as a design and measurement problem. It connects the earlier distinctions among token loss, instruction tuning, preference optimisation, inference, and RAG. Part V then turns to reasoning models and the additional question of how to evaluate multi-step computation.

Learning objectives

By the end of this chapter, you should be able to:

  • distinguish a capability benchmark, a reliability test, a safety evaluation, and a system evaluation;
  • define the population, unit, interface, and scoring rule for an LLM evaluation;
  • calculate an accuracy estimate and a simple confidence interval;
  • explain contamination, prompt sensitivity, and benchmark overfitting;
  • separate model, retrieval, tool, and decoding failures in a system trace;
  • identify when aggregate scores conceal subgroup or task differences; and
  • specify an evaluation report that can be audited and reproduced.

Running evaluation

The running test has labelled inputs, a fixed template, a checkpoint, a decoding policy, and an exact-match criterion. Changing any of these can change the reported score.

Level 1 - Intuition

Scores answer bounded questions

Exact accuracy on multiple-choice questions measures success on those items under the supplied prompt and answer extraction rule. A factuality evaluation measures a different property. A safety red-team, long-context retrieval test, code execution task, and human preference study each answer other questions. A broad evaluation programme may combine them, but their scores should not be collapsed into one claim without explaining the aggregation and the uses it represents.

Benchmark choice defines which errors are visible. A test with short English questions can miss multilingual performance, tool failures, source use, refusal behaviour, latency, and long-document reliability. A test with a fixed answer key can be appropriate for a narrow capability while being unsuitable for an open-ended assistant response.

Code 
items=[True,True,False,True,False,True,True,False,True,True]
accuracy=np.mean(items)
print("accuracy:",accuracy,"n:",len(items))

Reliability requires repeated and varied evidence

One successful answer does not estimate how often a system will succeed. Reliability concerns the distribution of outcomes across relevant inputs, including rare but consequential failures. For stochastic generation, the same input can yield different outputs. For tools and retrieval, external state can change. Evaluation should therefore record repetitions, seeds or sampling settings, versions, and the time at which an external collection was queried.

Level 2 - Measurement mechanics

The unit and denominator determine a metric

An accuracy denominator can be questions, examples, claims, generated tokens, tool calls, or complete episodes. These choices are not interchangeable. A system that answers one question with five claims may be correct on some claims and not others. A RAG system may retrieve a relevant document but fail the final answer. The report should state the unit, inclusion rule, missing-data rule, and whether an item can receive partial credit.

For binary accuracy over (n) independent labelled units, a simple standard-error approximation is (). It is not sufficient for clustered, repeated, or adaptively sampled data, but it shows why a score from a small test set has substantial uncertainty.

Code 
p=.72; n=100
se=np.sqrt(p*(1-p)/n)
print("approximate 95% interval:",(round(p-1.96*se,3),round(p+1.96*se,3)))

Prompt and scorer choices are part of the treatment

Few-shot examples, system messages, answer options, retrieval context, tool permissions, temperature, and output parsing can all change a score. The evaluation should freeze or systematically vary these choices rather than treating them as invisible plumbing. Automatic scorers should be validated on a labelled subset, particularly when judging open-ended answers, code, citations, or safety properties.

Code 
predictions=["A","B","C","A"]
labels=["A","B","B","A"]
exact=[p==y for p,y in zip(predictions,labels)]
print("exact-match score:",np.mean(exact),"errors:",[i for i,x in enumerate(exact) if not x])

Level 3 - Contamination and system boundaries

Contamination changes the interpretation of benchmark performance

If test items, answers, or close variants entered pretraining, fine-tuning, preference data, or prompt examples, benchmark performance can reflect prior exposure as well as generalisation. Exact-string searches are useful but insufficient because paraphrases, translated items, templates, and solutions can differ visibly while preserving the test content. A contamination policy should state search methods, source coverage, match thresholds, exclusions, and what score is reported when exposure is suspected.

Code 
test_item="What is the eligibility rule?"
training_texts=["Eligibility requires residence in the district.","What is the eligibility rule?","Other text"]
matches=[text for text in training_texts if test_item.lower() in text.lower()]
print("exact matches:",matches)

Contamination does not always make an evaluation useless, but it narrows the claim. A score may still measure retrieval from memorised material or performance under known exposure. It should not be presented as evidence of behaviour on unseen instances without a defensible boundary.

Evaluate complete systems at component boundaries

An LLM application can include a model, prompt template, decoder, retriever, index, tools, output validator, and user interface. A final failure may originate in any of these. The evaluation trace should retain input tokens, retrieved IDs, tool calls and outputs, generated IDs, validator decisions, and the final displayed answer. This supports component-level measurements and repair.

Code 
trace={"retrieval":"relevant chunk missed","tool":"not called","generation":"unsupported answer","validator":"passed"}
print(trace)

Level 4 - Evaluation design and reporting

Build an evaluation around a decision

The intended decision should determine the test: whether to deploy a model version, select an adaptation, allow a tool action, use a retrieval corpus, or claim performance for a population. Define the target inputs, harm or cost of errors, baseline, required confidence, and stopping rule before inspecting the result. This prevents a convenient benchmark from becoming a proxy for a different deployment decision.

Code 
evaluation_plan={"decision":"deploy retrieval update","population":"current policy queries","baseline":"index-v11","primary":"supported-answer rate","guardrail":"no access-control failures"}
print(evaluation_plan)

Report disaggregated evidence and limits

An audit report should state model, tokenizer, prompt, decoding, tools and index versions; test construction and dates; item counts and strata; scoring and adjudication; uncertainty; contamination checks; excluded cases; failures; cost and latency; and known limits. Where human judgements are used, report judge instructions, information access, agreement, and aggregation. Where benchmarks are public, report whether they may have influenced development.

Reliability includes calibration and failure concentration

An evaluation can ask whether a model’s expressed confidence or probability is related to correctness. Calibration is not solved by a single overall accuracy: a system may be reliable on routine examples and confidently wrong on one task slice. When a system does not expose calibrated probabilities, a proxy such as self-reported confidence, verifier score, or retrieval support should be treated as a separate predictor and evaluated against outcomes.

Failure concentration also matters. Ten errors distributed across low-stakes formatting tasks have different implications from ten errors concentrated in access-control, medical, or financial cases. An evaluation report should preserve error categories and severity rules, rather than allowing a broad average to conceal the decision consequences of a rare failure.

Code 
outcomes=[{"slice":"routine","correct":1,"confidence":.8},{"slice":"high-stakes","correct":0,"confidence":.95},{"slice":"routine","correct":1,"confidence":.7}]
for row in outcomes: print(row)

Benchmark development is itself an intervention

Once a benchmark is public and used repeatedly for model selection, prompt design, data filtering, or reward design, its score can become a target. This can improve performance on the benchmark while narrowing the evidence it provides about unseen work. Held-out sets, refreshed item pools, task variants, and preregistered evaluation protocols can reduce this risk, but none removes the need to describe the development history.

Code 
development={"public_benchmark_used_for_tuning":True,"hidden_holdout":True,"prompt_fixed_before_holdout":True}
print(development)

Common misconceptions

  • A high benchmark score establishes general intelligence. It measures performance under a specific evaluation contract.
  • A single accuracy is enough for deployment. Slice performance, uncertainty, reliability, cost, and failure consequences may differ.
  • Public benchmarks are necessarily uncontaminated. Development and training exposure require explicit assessment.
  • A final wrong answer is always a model failure. Retrieval, tools, prompts, validators, and interfaces can fail first.
  • Automatic judging removes evaluation subjectivity. It introduces a scorer model and its own validation requirements.
  • More benchmarks automatically improve evidence. They can duplicate a narrow distribution or encourage benchmark-specific optimisation.
